Is the KiCad-trained linker inaccurate on WACV photos?

With clean input boxes, no: the same linker links 92.9 % of the labelled parts to the right text box. With the real OCR boxes of the end-to-end pipeline, it links only 52 % of the parts that the detector and OCR both found. The loss comes from the input boxes, not from the photos.

What goes wrong with all OCR boxes (input C)

Wrong text: a box on the part itself

459 of the 518 wrong links · random 24 shown

The chosen box sits on a pad, on the component body, or on a value marking such as "103". The real label is right next to the part. The KiCad training data never has a text box on a part body (the data build drops labels that lie at least half inside a footprint), so the linker learned that the nearest box is the label, and a box on the body is always the nearest.

None: the label has a box, but the link is not confident

982 parts · random 18 shown

OCR found the label, but the linker's best probability is below 0.5 (587 cases) or it chose none (395). The extra boxes near the part share the probability with the label.

What this means for the Claude reader

The class result with Claude as the reader (mAP50 0.586, F1 0.743, against detector 0.541 / 0.729) uses input C. A better reading helps only where the link is right, and in C only 1,635 of 4,185 labelled parts (39 %) reach their right text. So the reader is not the limit now; the text boxes given to the linker are.

Proposed next tests (not run)

  1. Drop OCR boxes on part bodies. Before linking, remove each OCR box that lies at least half inside a detector box. This is the same rule as the KiCad data build, so it needs no new threshold and no training. Check on the 3 dev photos, then report on the 42 test photos.
  2. Train with junk boxes. Run the OCR detector on the KiCad renders; every box that is not a reference label becomes an extra text token with its PARSeq feature and the target "none". The linker then sees the same kind of input as on photos.
