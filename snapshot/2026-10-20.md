**Assistant** (04:46 UTC)

你问到了关键点。link accuracy 的计算方式如下（`tools/linkformer.py` 里的 `count()` 和 `summarize()`）：

## 1. 评估设定（oracle track）
- 输入是 **GT 的元件框 + GT 的文字框**（clean_test41 = 清理过的 WACV 41 张测试照片），不是 detector 和 OCR 的输出。所以这个指标只衡量 linker 本身。

## 2. 每个 part 的预测 link 怎么来
- **基线**：模型输出分数矩阵 → 每行 log-softmax → **Hungarian**（每个 part 还有自己的 none 列），得到**一对一**的分配。
- **AR head**：逐步贪心解码（被占用的文字屏蔽），得到的 logits 再交给同一个 decode 函数。因为贪心结果本身已经是一对一，Hungarian 得到的就是贪心的选择。

所以你说得对：**基线和 AR 都是在一对一约束下评估的**。

## 3. 指标公式
- **accuracy** = right / linkable
  - linkable = 有目标文字的 part（它的 designator 印在板子上，并且有文字框标注）
  - right = 预测的文字属于这个 part 的目标集合（目标集合 = 字符串和它的 designator 相同的所有文字框，或者显式标注的 link）
- **precision** = right / links，links = 所有被分配了文字的 part（包括本来没有 label 但被硬分配了一个文字的 part）
- 标记为 ignore 的 part 不计入。

## 4. 这说明了什么
这次的对比**其实是"Hungarian（全局最优的一对一）"对"AR 贪心（顺序决定的一对一）"**。原来的评估里一对一约束已经存在了，所以 AR head 在 link accuracy 上几乎不可能靠"保证唯一性"获得提升。它唯一可能的贡献是"根据前面的决定调整后面的分数"，而结果显示这部分作用很小。

这也解释了为什么在 C 上也没有变化：C 原来没有一对一约束，加上以后，好处和"前面错一个、后面连锁错"的坏处基本抵消。

所以这个实验的结论应该更准确地表述为："**在已经有 Hungarian 一对一约束的情况下，再加一个可学习的顺序解码，没有带来额外收益**"，而不是"一对一约束没用"。

软读字是什么意思

**Assistant** (06:10 UTC)

**"读字"** 指的是：OCR 看文字框，判断上面写的是什么。区别在于 OCR 输出怎么用：

## 硬读字（hard reading）
OCR（PARSeq）每个字符位置只取**最可能的那个字符**，拼成一个字符串，然后查前缀表。

例如一个模糊的 `R12`，第一个字符 PARSeq 认为是 R 的概率 0.55，是 B 的概率 0.40：
- 硬读字取 R → 字符串 `R12` → 查表 → **resistor**（100 % 相信这个结果）。
- 如果它取错成 B → `B12` → 表里没有 B → 判不出 class。

## 软读字（soft reading）
保留 PARSeq 每个字符位置上**所有字符的概率**，按前缀表算每个 class 的概率：
- P(以 R 开头且后面是数字) ≈ 0.55 → resistor 0.55
- P(以 B 开头且后面是数字) ≈ 0.40 → B 不在前缀表里 → 这部分算"不像 designator"，交给 detector
- 结果：resistor 0.55，剩下的 0.45 按 detector 的判断分配。

也就是说，**OCR 不确定的时候，软读字会把不确定性保留下来**，不会因为读错一个字母就整个判错。然后再和 detector 的意见按比例混合。

前面那个 R341 的例子（读成 `341`，丢了 R）说明了软读字的局限：如果 OCR 在第一个位置上根本没给 R 任何概率，软读字也救不回来。
